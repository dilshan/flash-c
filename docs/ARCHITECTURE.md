## 1. Overview

```
source ──► lexer/preprocessor ──► parser + type checker ──► optimizer ──► x86-64 code generator ──► ELF file
 (cpp.c)        (cpp.c)               (parse.c)             (opt.c)               (gen.c)
```

| Directory | Contents |
|---|---|
| `src/compiler/` | `cpp.c` lexer and preprocessor, `parse.c` parser and type checker, `opt.c` optimizer, `gen.c` code generator and ELF writer, `compile.c` driver, `fc.h` public interface, `fci.h` internals |
| `src/ide/` | the text-mode IDE (section 6) and the debugger (section 7) |
| `src/cli/` | the `fcc` main program |
| `runtime/` | the run-time library in Flash C and its headers (section 5) |
| `help/` | extended online help, generated by `tools/helpgen` |
| `tests/`, `tools/` | tests (section 10) and generators |

The IDE links the same compiler as `fcc`, so both always behave alike.

## 2. Compiler front end

* **One address space, one arena.** All compiler data lives in a bump arena (`util.c`) that is
  released wholesale at the start of the next compile, so the IDE can call `fc_compile()` over and
  over without leaking. Identifiers are interned (pointer comparison).
* **Preprocessor** (`cpp.c`). The lexer produces a token vector, directives are executed on the
  vector, and macros are expanded recursively with a "busy" flag instead of hide-sets. Built-in
  headers are looked up by name after the user's include directories.
* **Parser** (`parse.c`). A recursive-descent parser that builds a *typed* AST in one pass: every
  `Node` has its C type, implicit conversions are explicit `N_CAST` nodes, pointer arithmetic is
  already scaled, and integer and floating constants are folded. Semantic errors are reported with
  the classic wording and the parser recovers at statement boundaries (`setjmp`/`longjmp`), so one
  run reports many errors.
* **Types.** `char` = 1, `short` = 2, `int` = 4, `long` = 8, pointer = 8, `float` = 4, `double` = 8.
  Integer values are kept *normalised* in 64-bit registers (sign- or zero-extended according to
  their type), so comparisons and shifts only need the 64-bit forms.
* **Dead-code elimination.** While a function is parsed it records the globals and functions it
  references; only what is reachable from `main` and `_fc_start` is emitted.

## 3. Code generator and ELF writer

* **Code generator** (`gen.c`). A straightforward accumulator machine: every expression leaves its
  value in `rax`, and binary operators push the left operand. Floating values also travel in `rax`
  as their `double` bit pattern and are moved to `xmm0`/`xmm1` only for the arithmetic instruction
  (SSE2); `float` is stored in 4 bytes and widened on load.
* **Calling convention.** Private: arguments are pushed right to left (8 bytes each), the caller
  pops them, and the result is in `rax`. This makes `va_arg` trivial (`stdarg.h` is three macros)
  and means no ABI compatibility with the host libc is needed or attempted. Structures are passed
  by value by copying them into the argument slot; a structure result is built in a hidden frame
  slot of the caller whose address is passed as an extra first argument.
* **ELF writer.** One `PT_LOAD` segment (code, data, bss) at `0x400000`. With `-lw` there is an R+X
  segment for the header and code and a page-aligned R+W segment for data and bss; with `-lt` also
  `.symtab`, `.strtab` and section headers. Addresses are absolute 32-bit values with fixups
  resolved after layout. The entry stub calls the runtime function `_fc_start`, which calls `main`
  and `exit`.
* **Intrinsics** known to the code generator by name: `__syscall(n, args...)` (all system calls),
  `__sqrt`, and `__setjmp` and `__longjmp` (inline code: save or restore `rbp`, `rsp` and the
  resume address). The linker writes two stubs for kernel signal delivery (`__sigtramp`,
  `__sigrestorer`).
* **Code-generator switches.** `-Z` keeps a constant right operand in `rcx` instead of
  `push rax` / `pop rax` and removes `push rax; pop` pairs that are not separated by a label or
  line mark. `-O` drops a `jmp` to the next instruction and then relaxes the jumps of each function
  (rel32 to rel8 until a fixed point), remapping labels, fixups and the debugger line table. `-N`
  emits `cmp rsp, [__fc_stklimit]; jae; call __fc_stkover` in user functions; the limit is set by
  the start-up code from `RLIMIT_STACK` (`-ls` first applies the chosen size with `setrlimit`).
* **Link map** (`-M`, `-Mp`, `-Md`). `write_map` lists `_TEXT`, `_DATA`, `_BSS`, public symbols and
  the detailed segment map using the same symbol records.

## 4. The optimizer

`src/compiler/opt.c` runs on the tree of each function at the start of `gen_function`
(`opt_function`), after a once-per-program stage (`opt_program`). Each pass has its own `FCO_*` bit
in `FcOptions.opt_flags` (`fc.h`), switched with `-O:name`. The pass list and their effects are in
the [compiler reference](COMPILER.md#5-optimizations); this section says how they work.

`tests/opt.sh` checks each pass, and `tests/optfuzz.py` compiles random programs with and without
optimizations and compares their output.

### 4.1 Tree passes

Twelve passes work on expression trees: constant folding, algebraic simplification, constant
comparison evaluation, local constant and copy propagation, dead assignment elimination,
unreachable statement elimination, redundant cast elimination, canonicalization, local common
subexpression elimination (repeated pure expressions go through a new frame temporary), strength
reduction, and boolean and conditional simplification.

Data-flow facts exist only for local scalars whose address is never taken. They are joined at `if`,
dropped for variables assigned in loops, `&&`, `||`, `?:` and `switch`, and the data-flow passes
are skipped for functions with `goto` or labels, `setjmp`, or `volatile` anywhere in the program.
With debug information (`-v`) propagation, dead stores, CSE and unreachable-code removal are
skipped.

### 4.2 The block graph and control-flow passes

`cfg_build` splits a function into basic blocks (expression, condition, return and jump "atoms";
blocks for `if`, loops, `switch` and `case`, `break` and `continue`, `goto` and labels) and
`cfg_solve` runs an optimistic work-list analysis over it. What is known at the start of each block
(constants and copies of non-escaping local scalars) is the intersection over the incoming edges
that can be taken; a branch whose condition evaluates to a constant takes only one edge
(conditional constant propagation). `cfg_apply` then propagates the facts into the reachable blocks
and removes the code and labels of the blocks that were never reached.

* `cfg_live_dce` computes live variables backwards over the same graph and replaces assignments
  whose value is dead by their right-hand side.
* Jump threading retargets a `goto` whose label only holds another `goto`. Labels that no `goto`
  names any more are removed, which merges their block into the one before it; `if (c) goto L; L:`
  loses the jump.
* Tail-recursion elimination turns `return f(args);` inside `f` into assignments to the parameters
  (through temporaries) and a `goto` to a label at the start of the body. It only applies when
  every local and parameter is a scalar whose address is never taken.
* Functions with `setjmp` skip all of this. With debug information only expression-level passes
  run.

### 4.3 Loops and redundancy (`cfg_phase2`)

On the same block graph `graph_build` computes reachability, predecessors and dominators, and
`loops_find` turns every back edge `t -> h` (h dominates t) into a natural loop. It keeps a loop
only when it comes from a `while`, `do` or `for` statement and every block is dominated by the
header.

* **Reaching definitions** (a bit set over the assignments, with the value at entry as extra
  definitions) and the live variables decide whether an invariant assignment can leave a loop.
* **Available expressions** are a forward must-analysis over a universe of at most 128 pure,
  non-trapping expressions of local scalars; an atom that assigns one of the variables kills it.
* **Global CSE** rewrites every computation of an expression that is reused to `(t = e)` and every
  use that is available to `t`. **Partial redundancy elimination** first copies `e` to the end of a
  predecessor that lacks it.
* **Loop-invariant code motion** hoists an invariant assignment (when its variable is dead after
  the loop and every use sees only that definition) or an invariant subexpression into a block
  placed before the loop.
* **Induction-variable optimization** replaces `i * c`, `i << c`, `(long)i * c` and `inv + i` by a
  temporary that is initialized before the loop and advanced next to the single update of `i`.
* Each transformation changes the tree, so the graph is rebuilt and the analyses are repeated (at
  most 24 rounds).

### 4.4 SSA form

With the dominator sets of `graph_build` the compiler derives the dominator tree and the dominance
frontiers (`domtree_build`), places phi functions for the tracked local scalars at the iterated
frontier of their assignments (only where the variable is live), and renames every definition and
use (`ssa_build`). An atom that is a plain assignment `x = e` defines one SSA value; any other atom
that assigns defines opaque values.

* **Sparse conditional constant propagation** (`sccp_run`) keeps a lattice value per SSA value and,
  per edge, whether it can be taken. It evaluates expressions with the constants of their operands
  (the same folding code as the tree optimizer) and then substitutes the constants.
* **Aggressive dead-code elimination** (`adce_run`) starts from the statements that must stay
  (conditions, returns, calls, stores, anything with an effect), marks the values they use, and
  removes every assignment that was never marked, including assignments that only feed each other
  in a loop. Branch conditions and statements are never removed by it, only assignments.

### 4.5 Alias analysis

With `alias` on, global CSE also treats loads of memory (globals, members, `a[i]` with a pure
index, `p->x`) as expressions. `loc_of` describes an access as a named object plus an offset, or
"through a pointer". Two accesses to different objects never overlap, accesses to the same object
overlap unless their constant ranges are apart, and a pointer access may overlap anything. A store,
or a call of a function that is not known to be pure, invalidates the loads it may touch. Partial
redundancy elimination never moves a load.

### 4.6 Inlining and whole-program passes

`opt_program` runs once, before any code is generated.

* **Call graph.** Tarjan's strongly connected components mark recursive functions (`Sym.rec`), and
  a greatest fixed point marks pure functions (no stores except to locals, no calls of impure
  functions, no `goto`, no endless loops).
* **Inlining** runs over all functions first. A call of a function whose body is `return expr;`
  over its scalar parameters is replaced by `expr`, with arguments that are not simple evaluated
  into temporaries first (at most three nested levels, never with debug information or
  `volatile`, never for recursive functions).
* **Interprocedural constant propagation** substitutes an argument that every call passes (and
  recursive calls pass through) as a constant.
* **Interprocedural dead-code elimination** replaces arguments the callee never reads by 0, drops
  the result of functions whose callers all discard it, deletes calls of pure functions whose
  result is unused, and removes the references to functions that are no longer called so that they
  are not emitted. A function whose address is taken, `main`, and library functions are left alone.
* **Accumulator introduction** (`accum_recursion`) rewrites `return n * f(n - 1)` and
  `return f(n - 1) + n` (integer `+` and `*` are associative) into a tail call plus an
  accumulator, which tail-recursion elimination turns into a loop.

### 4.7 Loop unrolling, unswitching and scalarization

* **Unrolling.** `for` loops with a counter, a constant bound and a constant step that run at most
  8 times are replaced by their copies. Other small loops without `break`, `continue` or `goto`
  run two iterations per test: `for (a; c; s) b` becomes
  `for (a; c;) { b; s; if (c) { b; s; } }`.
* **Unswitching.** An `if` inside a loop whose condition only uses local scalars the loop never
  assigns is moved out and the loop is duplicated (at most 4 per function).
* **Scalarization** (`sroa`). A local structure or array that is only accessed member by member, or
  element by element with constant indices (the parser writes those as `*(&v + offset)`), is
  replaced by one scalar per access, which the register allocator can then place in a register.

### 4.8 Register allocation and instruction selection

Run after the tree passes (`opt_regalloc`, `gen.c`).

* Locals chosen by use count (weighted by loop depth) live in `rbx` and `r12`-`r15`, which the
  prologue saves and the epilogue restores.
* Instruction selection uses immediate operands, loads a simple right operand straight into `rcx`,
  fuses a comparison with the branch that uses it, and branches on `!`, `&&` and `||` without
  materializing a boolean.
* Block layout folds `jcc l; jmp m; l:` into `jncc m` and rotates `while` and `for` loops so the
  test sits at the bottom.
* A tail call to another function pops its arguments into the caller's own argument slots,
  restores the registers, runs `leave` and jumps (only when every variable in the frame is a scalar
  whose address is never taken).

### 4.9 Profile-guided optimization and code size

* **`-Pg`** makes the code generator add a counter increment (`add qword [counter], 1`) at the
  entry of every function, before every `if` and loop, and at the start of their then part or body.
  The names of the counters are stored in the program's data, and `prof.c` (run-time library,
  `#pragma exit`) writes `name/kind/number/E|T count` lines when the program ends. Statements are
  numbered before optimization so that the same numbers are found again whatever the optimization
  switches.
* **`-Pu`** reads the file (`opt_profile_load`). The likely arm of an `if` with an `else` becomes
  the fall-through arm, hot functions are generated first, functions that never ran are optimized
  for size, hot callees get a larger inlining limit, and loops that average fewer than three
  iterations per entry are not unrolled.
* **`-Os`** (`size`) switches off unrolling, unswitching, partial redundancy elimination and loop
  rotation, and limits inlining to bodies of 3 nodes or functions with exactly one call.

## 5. The run-time library

The library is a set of small Flash C modules (`runtime/lib/`), embedded in the compiler by
`tools/embed.c` as a table of `{kind, name, text}`: kind `0` start-up (`c0.c`, always), `1` standard
library (`c/*.c`), `2` math library (`m/*.c`), `3` optional objects (`wildargs.c`). On every
compile the enabled modules are preprocessed and parsed together with the user's program (about
5 ms), under pseudo file names `c0/c0.c`, `libc/<name>.c` and `libm/<name>.c`. Each symbol
remembers its file, so the link map and the "module" in linker errors name the library module.

* **Hidden symbols.** Library symbols are hidden from the user's program until a header declares
  them, which keeps the classic diagnostics honest (`Call to function 'foo' with no prototype`,
  `Undefined symbol`). A user function with the same name as a library function wins for the
  program.
* **Linking is reachability.** Only functions reachable from `main`, the start-up code and the
  `#pragma startup` and `#pragma exit` functions of linked modules are emitted. A library module's
  pragma function is only kept if the module has another reachable symbol, so unused modules cost
  nothing.
* **Start-up** (`c0.c`). The ELF entry stub calls `_fc_start(argc, argv)`, which sets
  `_argc`, `_argv` and `environ`, runs the generated `__fc_init()` (the `#pragma startup` list,
  ascending priority), then `exit(main(...))`. `exit` runs the `atexit` handlers and the generated
  `__fc_exit()` (the `#pragma exit` list, descending priority, which flushes `stdio`), then `_exit`.
* **Floating point is detected, not declared.** The parser sets `uses_fp` when user code declares
  or computes with `float` or `double`; this links `fpcvt.c`, whose `#pragma startup` installs
  `__RealCvtVector` and `__ScanTodVector`. `printf` and `scanf` call the converters only through
  those vectors, so integer-only programs carry no floating-point code.
* **Private helpers.** Library-internal helpers are `static` functions with globally unique
  `__prefix` names (statics share one scope across modules). Libraries may not use compound
  literals.
* **Numerics.** `printf("%f")` uses an exact big-number decimal expansion of the binary value and
  rounds half to even, and matched glibc in every comparison in `tests/cases`. `math.h` is
  implemented with argument-reduced series (accuracy about 1e-15).

The function list is in the [library reference](LIBRARY.md), which `tools/gen_libdoc.py` generates
from the headers and the module sources.

## 6. The IDE

| File | Responsibility |
|---|---|
| `term.c` | raw terminal: alternate screen, off-screen cell buffer (char + CGA attribute), diff flushing, truecolor and 16-colour output, key and SGR-mouse decoding (CSI/SS3, Alt = ESC prefix, bracketed paste), SIGWINCH, restore on crash |
| `menu.c` | menu tables (items, shortcuts, hints), bar layout, pull-down and sub-menu navigation, mouse |
| `wm.c` | window list and z-order, Message, Output, Watch, Project and Register windows, status line, desktop, mouse (drag, resize, zoom, close, scroll bars) |
| `dialog.c` | dialog engine (inputs, check boxes, radio groups, buttons, lists, frames, custom items), flowing layout builder, message boxes, file dialog |
| `dialogs.c` | every Options dialog, Find/Replace, Go to line, Evaluate, Transfer, Colors and more |
| `editor.c`, `buf.c` | line buffer with undo and redo, cursor model, selection and blocks, WordStar-style commands, syntax highlighting, search including a small regex engine |
| `help.c` | hyper-linked help: built-in basic topics plus extended topics read from external `*.fch` files |
| `ide.c` | commands, build, make and run, Message tracking, projects, desktop file, main loop |
| `config.c` | colour table (named groups and items) and `fcconfig.fc` persistence |
| `dbgcore.c`, `dbgeval.c`, `debugger.c` | the debugger (section 7) |

Design points:

* **Immediate-mode drawing.** `ide_draw()` repaints the whole desktop into the cell buffer on every
  event; modal loops (menus, dialogs, `help_modal`) call it first and paint on top. The diffing
  flush keeps terminal traffic small.
* **User screen.** The IDE runs on the terminal's alternate screen. *Run* leaves it, restores the
  terminal modes, runs the program on the normal screen and comes back; *Alt+F5* peeks at it.
* **Transactional dialogs.** Settings dialogs edit `cfg` in place; *Cancel* restores a copy.
* **Help from dialogs.** A dialog's *Help* button calls `help_modal(topic)`, which opens the help
  window in front of the dialog and runs its own key loop until the window is closed.
* **Compiler integration.** The IDE links the same compiler library as `fcc`. Diagnostics arrive
  through a callback and are appended to the Message list; the first error is tracked in the editor
  automatically.

## 7. The debugger

* **Compiler side** (`-v` / `FcOptions.debug`). `gen.c` records a line table (`note_line`, one entry
  per statement start, in code order), user functions with their variables (frame offset, scope
  lines) and user globals, and exposes them as `fc_debug_info()` (`fc.h`, `FcDebug`). The data
  lives until the next compile.
* **`dbgcore.c`.** Runs the executable (a static ELF at fixed addresses) under `ptrace` with its
  stdio on a pseudo terminal. Breakpoints are `int3` bytes inserted only while the program runs.
  Trace and step single-step until the line changes; a `call` is detected from the opcode and
  stepped over with a temporary breakpoint at the return address (checking `rsp`, so recursion
  works). Frames are found by following the `rbp` chain; locals are `[rbp+off]`. The IDE switches
  to the user screen (`term_suspend`) only while the program runs freely; during that time keyboard
  input is forwarded to the pty.
* **`dbgeval.c`.** The expression evaluator (C operators on typed values read from
  `/proc/<pid>/mem`), value formatter, inspector lines, frame descriptions and registers.
* **`debugger.c`.** The UI: commands, the Breakpoints, Call stack and Inspect dialogs, the execution
  marker and desktop persistence. `ide_build` calls `dbgui_reset` first because a compile frees the
  debug tables.
* **Optimizations and debugging.** With debug information on, the optimizer skips every pass that
  would change statements, variable values or the call stack (section 4).

## 8. Help files

The basic documentation is compiled into `src/ide/help.c`. The extended help (the whole standard
library reference, formats, keywords, preprocessor) lives in `help/*.fch`, plain text files that
are read when help is first used. They are searched, in order, in `$FC_HELP`, `<exe>/help`,
`<exe>/../share/flashc/help`, `<exe>/../help`, `/usr/local/share/flashc/help`,
`/usr/share/flashc/help` and `./help`; the first directory with `.fch` files wins. If none is
found, only the basic topics are available and Contents says so.

File format:

| Line | Meaning |
|---|---|
| `@topic Title` | starts a topic (the same title replaces a built-in one) |
| `@append Title` | adds text to a topic |
| `@keys words` | words for Ctrl+F1 |
| `@alias names` | adds names to the Index |
| `@example` ... `@end` | program text (shown in the example colour, copied by Edit \| Copy example) |
| `{Title}` or `{label\|Title}` | a hyperlink |
| `;;` | a comment |
| `@@` at the start of a line | a literal `@` |

`help/library.fch` and `help/language.fch` are generated by `tools/helpgen/gen.py` (`make help`).
In the built-in topics, a line starting with `## ` begins a section, and lines should stay under 76
columns so they fit the help window.

## 9. Code style

The C sources (compiler, IDE, run-time library and tools) are formatted with `clang-format` using
the rules in `.clang-format` (4-space indent, 100 columns, braces on every block, a blank line
between definitions); run `make format` after editing. Every function has a comment that says what
it does, what its parameters mean and what it returns. The main structures (`Tok`, `Type`, `Sym`,
`Node`, `Win`, `Buf` and others) document their fields.

## 10. Tests

`make test` runs all of these.

| Test | What it checks |
|---|---|
| `tests/run.sh` | compiles each `tests/cases/*.c` with Flash C and with the host `gcc` and compares program output byte for byte (an optional `name.in` file is fed to stdin) |

| `tests/options.sh` | every command-line switch |
| `tests/opt.sh` | each optimization, and deep recursion and profile round trips |
| `tests/optfuzz.py` | random programs, compiled with and without optimizations, output compared |
| `tests/helpexamples.py` | compiles and runs every example in the help files, and checks line widths |
| `tests/libtest.sh` | the library build options: link maps, `-ln`/`-lnm`/`-f-`, `#pragma startup/exit` order, wildcard arguments, exit codes, `abort`, `atexit`, and that every public header compiles on its own |
| `tests/ide_smoke.py` | the real `fc` binary on a pseudo-terminal with a small VT emulator (`tests/tui.py`): types a program, compiles, runs, breaks it, follows the error, opens dialogs and help, quits |
| `tests/project_smoke.py` | projects and local options |
| `tests/debug_smoke.py` | the debugger in the real IDE: breakpoint, Run, Trace into, Call stack, Evaluate, Step over, Program reset, Go to cursor, program exit |

`tools/dbgtest.c` is a headless driver for `dbgcore`, used while developing. `tools/screenshots.py`
drives the IDE the same way as the smoke tests and writes the pictures in `docs/screenshots`;
`tui.py` renders them with `render_png`.

## 11. Known gaps

* Language: compound literals, variable-length arrays, a distinct `long long`, and `long double`.
* Library: locale-independent `strftime` and `time.h` details.
* Optimizer: a work-list SCCP, control-dependence in aggressive dead-code elimination, identical
  function folding, and wider alias information (see the limits in the
  [compiler reference](COMPILER.md#limits)).
* IDE: profile-guided optimization is only available on the command line.
